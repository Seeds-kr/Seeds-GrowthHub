# Seeds GrowthHub - 구현 로드맵 및 Phase 계획 v3

## 1. 문서 목적

이 문서는 Seeds GrowthHub의 구현 순서, 병렬 추진 과제, Phase별 목표, 산출물, 게이트 기준, 리스크를 정의한다.

이 문서는 특정 모집 일정에 종속되지 않는다. 모집/선발 기능은 운영 시스템의 주요 구성요소로 다루되, 특정 모집 실행 상세는 별도 관리한다.

## 2. 전체 구현 관점

1. 공통 기반을 먼저 만든다.
2. 운영 시스템을 실사용 가능한 수준으로 정리한다.
3. 신규 운영진 모집과 온보딩은 운영 시스템 구축과 병렬로 진행한다.
4. 성장 시스템은 성장모델·커리큘럼·운영모델이 확정되기 전에도 유지될 성장증거 계층부터 만든다.
5. 별도 축에서 Seeds 성장모델, 커리큘럼, 운영모델, 역할구조, 멘토링 구조를 정렬한다.
6. 정렬된 결과를 GrowthHub 기능과 데이터 구조에 반영한다.

## 3. 전체 Phase 구조

| 단계 | 명칭 | 핵심 목표 |
|---|---|---|
| Phase 1 | GrowthHub Core 기반 완성 | 사람, 역할, 권한, 기수, 팀, 문서, 가시성, 저장 전략 정리 |
| Phase 2 | GrowthHub Ops 운영 시스템 완성 | 회의, 작업, 운영 문서, 모집, 행사, 회계, 대시보드 정리 |
| Parallel A | 신규 운영진 모집 및 온보딩 | GrowthHub를 사용할 운영 조직 구성 |
| Phase 3 | GrowthHub Growth 안정 선개발 기능 완성 | 프로젝트, 스터디, 산출물, 피드백, 회고, 활동기록 기반 완성 |
| Parallel B | Seeds 성장모델·커리큘럼·운영모델 정렬 | 성장모델 중심으로 커리큘럼, 운영구조, 역할구조, 멘토링 구조 정렬 |
| Phase 4 | 정렬 결과의 GrowthHub 반영 | 성장해석, 커리큘럼 연계, 운영모델, 역할구조를 시스템에 반영 |

## 4. Phase 1: GrowthHub Core 기반 완성

### 4.1 목표

운영 시스템과 성장 시스템이 공유할 공통 기반을 만든다.

### 4.2 핵심 범위

- 사용자/프로필 관리
- role + extra_roles 기반 effective roles 유지
- scope 기반 권한 확장 검토
- 기수/프로그램/학생 구조 정리
- 팀/프로젝트 관계 정리
- 문서/템플릿 기반 구조
- Markdown 문서 저장 구조
- 파일/첨부 저장 전략
- visibility 정책
- 민감정보 접근 원칙
- 외부 도구 링크 구조

### 4.3 중간 산출물

- 사용자/역할/권한 모델
- 용어 표준
- 기수/프로그램/학생 구조 정리
- 문서/템플릿 데이터 구조 초안
- 파일 저장 전략
- 외부 연계 원칙
- visibility 정책 초안

### 4.4 게이트 기준

- 한 사람이 여러 역할을 가질 수 있다.
- 기수/프로그램/학생/프로젝트의 기본 관계가 정리되어 있다.
- 운영진, 멘토, 학생, 평가 surface의 접근 범위가 구분되어 있다.
- 문서와 첨부파일의 저장 원칙이 정해져 있다.
- 민감정보와 visibility 정책이 최소 수준으로 반영되어 있다.

### 4.5 리스크

- Admin과 운영진을 혼동할 수 있다.
- Program의 의미가 커리큘럼 논의 전에 고정될 수 있다.
- visibility 정책이 늦어지면 피드백/회고 신뢰 문제가 생길 수 있다.
- Google Drive와 자체 저장소의 역할이 불명확하면 자료가 다시 흩어질 수 있다.

## 5. Phase 2: GrowthHub Ops 운영 시스템 완성

### 5.1 목표

Seeds 운영진이 실제 운영 업무를 GrowthHub에서 수행할 수 있게 한다.

### 5.2 핵심 범위

- 회의록 관리
- 후속 액션 / 작업관리
- Markdown 운영 문서 / 템플릿 / 체크리스트
- 모집/선발 관리
- 평가 surface
- 면접 일정 관리
- 정기모임/행사 관리
- 출석 관리
- 회계/정산 관리
- 공지/커뮤니케이션
- 운영 대시보드

### 5.3 중간 산출물

- 회의록 화면
- 작업 칸반
- 운영 문서 편집기
- 템플릿/체크리스트 라이브러리
- 모집/평가/면접 운영 화면
- 행사/세션 관리 화면
- 회계/정산 화면
- 운영 대시보드

### 5.4 게이트 기준

- 회의록에서 후속 액션을 생성할 수 있다.
- 작업에는 담당자, 마감일, 상태가 있다.
- 운영 문서를 Markdown으로 작성·편집·미리보기할 수 있다.
- 모집/평가/면접 흐름이 권한 원칙에 맞게 작동한다.
- 정기모임/행사에 체크리스트와 출석을 연결할 수 있다.
- 회계 증빙과 정산 상태를 관리할 수 있다.
- 운영 대시보드에서 지연 작업과 운영 리스크를 볼 수 있다.

### 5.5 리스크

- 운영 문서 편집기가 약하면 운영진 온보딩 가치가 떨어진다.
- 작업관리가 프로젝트 이슈관리까지 확장되면 범위가 과도해진다.
- 회계 증빙 권한이 약하면 신뢰 문제가 생긴다.
- 외부 연계 범위가 커지면 핵심 운영 기능이 지연될 수 있다.

## 6. Parallel A: 신규 운영진 모집 및 온보딩

### 6.1 목표

GrowthHub를 실제로 사용할 운영 조직을 구성한다.

### 6.2 핵심 작업

- 운영진 역할 정의
- 신규 운영진 필요 포지션 확정
- 역할별 기대 책임 정리
- 기대 투입 시간 정리
- 온보딩 문서 준비
- GrowthHub 사용 가이드 준비
- 첫 2주 업무 설계
- 운영진 인수인계 구조 마련

### 6.3 중간 산출물

- 운영진 역할표
- 신규 운영진 모집 포지션 정의
- 기대 투입 기준
- 온보딩 체크리스트
- 첫 2주 업무표
- GrowthHub 사용 원칙
- 인수인계 템플릿

### 6.4 게이트 기준

- 모집할 역할이 명확하다.
- 역할별 책임과 기대 투입이 설명 가능하다.
- 신규 운영진이 사용할 기본 문서와 시스템 화면이 있다.
- 첫 2주 업무가 구체화되어 있다.

### 6.5 리스크

- 역할이 추상적이면 지원자가 무엇을 할지 이해하기 어렵다.
- GrowthHub 사용법이 정리되지 않으면 신규 운영진이 시스템을 우회할 수 있다.
- 멘토와 운영진의 경계가 흐려질 수 있다.

## 7. Phase 3: GrowthHub Growth 안정 선개발 기능 완성

### 7.1 목표

성장모델·커리큘럼·운영모델이 확정되기 전에도 유지될 가능성이 높은 성장증거 계층을 구현한다.

### 7.2 핵심 범위

- 프로젝트 기본정보
- 프로젝트 멤버/역할
- 멘토 연결
- 산출물 링크
- GitHub/데모/발표자료 링크
- 스터디 기본정보
- 스터디 참여자
- 피드백 최소 기록
- 회고
- 활동기록
- 팀 상태 체크
- 임시 태그

### 7.3 중간 산출물

- 프로젝트 관리 화면
- 프로젝트 멤버/역할 관리
- 산출물 등록/가시성 관리
- 스터디 관리 화면
- 회고 작성 화면
- 멘토 피드백 화면
- 팀 상태 체크 화면
- 성장증거 대시보드 초안

### 7.4 게이트 기준

- 프로젝트와 학생/멘토/산출물을 연결할 수 있다.
- 스터디와 참여자/산출물을 연결할 수 있다.
- 멘토가 담당 팀에 대해 짧은 피드백을 남길 수 있다.
- 학생 또는 팀이 회고를 남길 수 있다.
- 운영진이 팀별 상태와 지원 필요사항을 볼 수 있다.
- 태그는 최종 역량 태그가 아니라 임시 분류 태그로 사용된다.

### 7.5 리스크

- 성장증거가 평가로 오해될 수 있다.
- GitHub 지표가 기여도 평가처럼 사용될 수 있다.
- 회고 공개 범위가 부적절하면 학생 신뢰가 낮아질 수 있다.
- 멘토 입력 요구가 길어지면 멘토 부담이 커진다.

## 8. Parallel B: Seeds 성장모델·커리큘럼·운영모델 정렬

### 8.1 목표

Seeds가 어떤 성장을 만들 것인지, 그 성장을 어떤 커리큘럼·운영모델·역할구조·멘토링 구조로 실현할 것인지 정렬한다.

### 8.2 포함 범위

- Seeds 인재상
- 성장모델
- 성장 단계
- 핵심 역량 또는 성장 기준
- 커리큘럼 구조
- 프로젝트/스터디/멘토링/정기모임의 역할
- 운영모델
- 운영진 역할구조
- 멘토링 구조
- 학생 경험 여정

### 8.3 정렬 프레임

```text
Goal
  Seeds가 만들고 싶은 학생 성장

Structure
  그 성장을 만들기 위한 커리큘럼, 운영모델, 역할구조, 멘토링 구조

Realization
  그것을 실제로 운영하고 기록하기 위한 GrowthHub 기능과 데이터 구조
```

### 8.4 중간 산출물

- Seeds 성장모델
- 커리큘럼 구조
- 운영모델/운영구조
- 역할구조
- 멘토링 구조
- 학생 경험 여정
- 시스템 반영 요구사항

### 8.5 게이트 기준

- Seeds가 만들고 싶은 성장상이 설명 가능하다.
- 커리큘럼과 활동이 성장모델과 연결된다.
- 운영모델과 역할구조가 성장모델 실현에 맞게 정렬된다.
- 멘토링 구조와 운영진 구조의 경계가 설명 가능하다.
- GrowthHub에 반영해야 할 기능과 데이터가 도출된다.

### 8.6 리스크

- 성장모델이 운영구조를 과도하게 단순화할 수 있다.
- 운영구조가 성장모델 실현과 분리될 수 있다.
- 커리큘럼이 시스템 기능을 지나치게 복잡하게 만들 수 있다.

## 9. Phase 4: 정렬 결과의 GrowthHub 반영

### 9.1 목표

Parallel B에서 정렬된 성장모델, 커리큘럼, 운영모델, 역할구조를 GrowthHub에 반영한다.

### 9.2 핵심 범위

- 성장 단계 반영
- 역량 또는 성장 태그 재정의
- 커리큘럼 모듈 연결
- 활동별 성장 목표 연결
- 학생별 성장 리포트
- 멘토 인사이트
- 운영진 대시보드
- 역할구조와 권한 구조 반영
- 운영모델 기반 프로세스/게이트 반영

### 9.3 중간 산출물

- 성장모델-데이터 매핑표
- 커리큘럼-활동 매핑표
- 역할구조-권한 매핑표
- 학생 성장 리포트 초안
- 멘토 인사이트 화면
- 운영진 성장/운영 대시보드

### 9.4 게이트 기준

- 성장모델의 핵심 개념이 시스템 객체와 연결된다.
- 커리큘럼과 프로젝트/스터디/멘토링/정기모임이 연결된다.
- 운영모델과 역할구조가 권한/프로세스에 반영된다.
- 학생·멘토·운영진이 각자 필요한 성장/운영 인사이트를 볼 수 있다.

### 9.5 리스크

- 성장모델 반영이 점수화로 과도하게 흐를 수 있다.
- 학생 리포트가 평가표처럼 인식될 수 있다.
- 권한 구조가 운영 역할 변화를 따라가지 못할 수 있다.

## 10. 전체 의존관계

| 선행 요소 | 후행 요소 |
|---|---|
| 용어 표준 | 모든 문서와 구현 명세 |
| Core 역할/권한 | 평가, 회계, 피드백, 회고 접근 제어 |
| 기수/프로그램/학생 구조 | 행사, 과제, 프로젝트, 성장기록 |
| 문서/템플릿 구조 | 운영 문서, 체크리스트, 온보딩 |
| 외부 도구 연계 원칙 | GitHub, Discord, Drive, Calendar, Email/SMS 연동 |
| Ops 기능 | 운영진 실사용과 운영 안정화 |
| Growth 증거 계층 | 향후 성장모델 기반 해석 |
| Parallel B 정렬 결과 | Phase 4 성장/운영 모델 반영 |

## 11. 현재 판단

현재 로드맵의 핵심은 GrowthHub를 완성된 논리의 산출물이 아니라, 논리와 구현이 상호 보완되는 운영·성장 인프라로 구축하는 것이다.

Phase 1~3은 바뀌지 않을 기반과 실행 기능을 만들고, Parallel B에서 성장모델·커리큘럼·운영모델·역할구조를 정렬한 뒤 Phase 4에서 반영한다.
