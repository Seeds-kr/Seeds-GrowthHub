# UX 결함 기록 (1단계)

> 2026-08-03 · 실제 브라우저(Playwright, 1440×900) 주행 결과.
> 의견이 아니라 **측정값**을 적는다. 판정 기준은 `PRODUCT.md`의 세 사용자가 동시에
> 존재한다는 것 — 신규 운영진이 헤매면 실패다.

## F1 — 앱 전체 버튼에 호버 피드백이 없다 · 심각

사용자 신고("호버해도 아무것도 안 변해서 클릭되는 버튼인지 모르겠다")를 재현했고
**근본 원인까지 확인했다.**

측정값 (`/admin/users`, 1440px):

| 대상 | 호버 시 변화 | cursor |
|---|---|---|
| 테이블 행 액션 버튼 | **없음** | `default` |
| 주요 버튼(primary) | **없음** | `default` |
| 네비 링크 | **없음** | `pointer` |

원인은 화면이 아니라 `components/ui/button.tsx` 한 곳이다. 모든 variant에서 hover가
**의도적으로 제거**돼 있고(`// @replit: no hover` 주석) 그 자리에 커스텀 유틸리티
`hover-elevate` · `active-elevate-2`가 들어갔는데,

```
사용처: button.tsx · badge.tsx · pages/admin/finance.tsx
정의:   index.css 0건, 빌드된 CSS 0건
```

**정의가 어디에도 없다.** 존재하지 않는 클래스라 아무 효과가 없다. 즉 앱 전체 버튼이
호버에 반응하지 않는 것은 개별 화면의 마감 문제가 아니라 컴포넌트 결함이다.

`cursor: default`도 같이 걸린다 — `<button>`의 브라우저 기본값이고 shadcn은 `cursor-pointer`를
넣지 않는다. 호버 색 변화가 없는 상태에서 커서까지 화살표면 클릭 가능하다는 단서가 0이다.

**고칠 위치:** `button.tsx`(+`badge.tsx`) 한 곳. 화면 수만큼 반복할 일이 아니다.

## F2 — 키보드 포커스는 정상 (결함 아님)

처음에 결함으로 적었다가 **내 검사가 틀린 것**으로 판명됐다. `.focus()`는
`:focus-visible`을 발동시키지 않는다. 실제 Tab으로 다시 재니:

```
Tab 포커스 대상: A "프로그램(Programs)"
outline: auto 1px rgb(97, 104, 117)   → 시각 표시 있음
```

브라우저 기본 outline이 살아 있고 `focus-visible:ring-1`도 정의돼 있다. 손대지 않는다.

## F3 — 신규 운영진 첫 화면은 통과

`/admin`에서 온보딩 카드가 노출된다. 역할별 다음 단계와 온보딩 문서 링크가 보인다.

## F4 — 빈 상태에 진입 버튼은 있으나 안내가 없다 · 중간

`/admin/announcements`: "공지가 없습니다." + `+ 새 공지` 버튼.
`/admin/meetings`: `+ 새 회의` 버튼.

버튼이 있다는 점은 F4를 치명적이지 않게 만든다. 다만 **무엇을 왜 만들어야 하는지**가
없어서, 처음 온 사람은 "공지를 지금 써야 하나?"를 스스로 판단해야 한다.
`PRODUCT.md` 원칙 4(막다른 길을 만들지 않는다)의 약한 버전이다.

## F5 — 출석 집계 첫 화면은 기수 선택을 요구 · 낮음

`/admin/attendance`는 기수를 고르기 전까지 빈 화면이고 "기수를 선택하면 …" 안내가 있다.
기수가 하나뿐인 초기 운영에서는 **자동 선택**이 나을 수 있다. 규모 20~40명·기수 1개
기준에서는 선택 단계가 순수 마찰이다.
